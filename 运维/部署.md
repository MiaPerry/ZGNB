## 一、先建立概念：服务器上跑的是什么

你的阿里云服务器上有三样东西在干活：

```
访客浏览器 ──→ ① Nginx（网站服务器）
                │  职责A：把「网页文件」发给访客    → 文件放在 /www/zgnb/webroot/
                │  职责B：把 /api 请求转给后端      ↓
                ② zgnb-api（Python 后端程序）
                │  职责：所有计算（指标、选股、诊断）→ 监听 8000 端口
                ↓
             ③ stock_data.db（SQLite 数据库文件）  → /www/zgnb/data/
```

**关键认知：你电脑上的代码和服务器上的代码是两份完全独立的东西。**
你在本地改了代码，服务器**什么都不会发生**——直到你手动把最新成果传上去。这个“传上去并让服务器用上”的动作，就是“更新部署”。

## 二、为什么前端和后端的更新方式不一样

| | 前端（frontend/） | 后端（api/、modules/） |
|---|---|---|
| 你改的文件 | `.tsx` `.ts` `.css` | `.py` |
| 浏览器/服务器能不能直接跑 | ❌ 不能。React/TS 源码要经过 **vite build 翻译**成普通 HTML/JS | ✅ 能。Python 直接跑源码 |
| 更新动作 | 本地**编译** → 把编译产物 `dist/` 传上去 | 把 `.py` 文件传上去 |
| 要重启吗 | **不用**。Nginx 每次都读最新文件，传完立即生效 | **要**。Python 只在启动时读一遍代码，传完必须重启 `zgnb-api` |
| 生效确认 | 浏览器 **Ctrl+F5** 强制刷新（避开缓存） | 重启后看健康检查接口 |

一句话记忆：**前端是“做好菜端上桌”，后端是“传菜谱进厨房并让厨师重开火”。**

## 三、三种更新场景（手动版，帮你理解每一步）

### 场景 A：改了前端代码（页面、组件、样式）

```powershell
# ① 进入前端目录（us 分支的代码在这里）
cd d:\myProject\ZGNB-main\ZGNB-main\.worktrees\us\frontend

# ② 编译（把 React 源码翻译成浏览器能跑的文件，产物在 dist/ 文件夹）
npm run build

# ③ 把编译产物打包
tar -c -a -f "$env:TEMP\zgnb-web.zip" -C dist .

# ④ 上传到服务器
scp -i $env:USERPROFILE\.ssh\zgnb_deploy_key "$env:TEMP\zgnb-web.zip" root@182.92.196.8:/root/

# ⑤ 在服务器上：清空旧网页 → 解压新网页 → 删安装包
ssh -i $env:USERPROFILE\.ssh\zgnb_deploy_key root@182.92.196.8 "rm -rf /www/zgnb/webroot/* && cd /www/zgnb/webroot && unzip -oq /root/zgnb-web.zip && rm /root/zgnb-web.zip"
```
做完浏览器 **Ctrl+F5** 就能看到新版页面。

### 场景 B：改了后端代码（api/ 或 modules/ 里的 .py）

```powershell
# ① 进入项目根目录
cd d:\myProject\ZGNB-main\ZGNB-main\.worktrees\us

# ② 打包所有后端代码（整目录打包，不用管具体改了哪个文件）
tar -c -a -f "$env:TEMP\zgnb-code.zip" --exclude "__pycache__" -C . api modules rules knowledge scripts .env requirements.txt

# ③ 上传
scp -i $env:USERPROFILE\.ssh\zgnb_deploy_key "$env:TEMP\zgnb-code.zip" root@182.92.196.8:/root/

# ④ 服务器解压 + 重启后端（重启 = 让 Python 重新读一遍新代码）
ssh -i $env:USERPROFILE\.ssh\zgnb_deploy_key root@182.92.196.8 "cd /www/zgnb && unzip -oq /root/zgnb-code.zip && rm /root/zgnb-code.zip && systemctl restart zgnb-api"
```

### 场景 C：本地同步了新数据，想让服务器也有

```powershell
scp -i $env:USERPROFILE\.ssh\zgnb_deploy_key data\stock_data.db root@182.92.196.8:/www/zgnb/data/
ssh -i $env:USERPROFILE\.ssh\zgnb_deploy_key root@182.92.196.8 "systemctl restart zgnb-api"
```

⚠️ **方向要记住：本地 → 服务器是“覆盖”**。如果你在**网页上**加过自选股（存在服务器数据库里），这一步会把它们冲掉。数据库只适合“本地为准”的更新思路。

## 五、日常更新流程（以后的固定动作）

```powershell
cd D:\myProject\ZGNB-main
.\update_server.ps1
```

它会自动完成：**编译前端 → 传前端 → 传后端 → 重启 → 健康检查**，最后看到绿色的 `[OK] 线上服务正常` 就说明部署成功了。

**按需选择**（更新越少越快）：

| 你的情况 | 命令 | 耗时 |
|---|---|---|
| 改了前端或前后端都改了（不确定就用这个） | `.\update_server.ps1` | 约1分钟 |
| 只改了页面/组件/样式（frontend/src 下） | `.\update_server.ps1 -Frontend` | 约40秒 |
| 只改了 .py（api/ 或 modules/ 下） | `.\update_server.ps1 -Backend` | 约10秒 |
| 本地同步了新数据想推上线 | `.\update_server.ps1 -Db` | 约1分钟 |

> 首次运行如果 PowerShell 提示“**禁止运行脚本**”，先执行一次 `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`，选 Y，以后就不会再问了。

> 注意：脚本固定读取 **us 分支**的代码（`ZGNB-main\.worktrees\us` 这个目录）。你平时改代码就是改这个目录里的文件，改完跑脚本即可。

## 六、出问题了怎么办（三板斧排查）

**第 1 斧：先看网站还活着吗**
```powershell
curl.exe -u "perry:<访问密码>" http://182.92.196.8/api/v1/system/health
```
返回 `{"status":"ok",...}` = 后端活着，问题在前端或网络；返回别的/超时 = 后端挂了，看第 2 斧。

**第 2 斧：看后端日志（90% 的错误原因都在这里）**
```powershell
ssh -i $env:USERPROFILE\.ssh\zgnb_deploy_key root@182.92.196.8 "journalctl -u zgnb-api -n 50 --no-pager"
```
看最后 50 行日志，Python 报错（红色 Traceback）会直接告诉你哪个文件哪一行出了问题。

**第 3 斧：万能重启大法**
```powershell
ssh -i $env:USERPROFILE\.ssh\zgnb_deploy_key root@182.92.196.8 "systemctl restart zgnb-api"
```
后端配置了崩溃自动拉起，一般不用手动救；如果改了新代码反而报错，最可能是本地代码本身有 bug——回本地跑 `python -m pytest tests/ -v` 验证一下，修好后再跑一次更新脚本就恢复了。

## 七、心智模型总结（记住这三句就够了）

1. **改代码 ≠ 上线**：本地改完只是在你电脑上生效，跑 `.\update_server.ps1` 才是上线。
2. **前端要编译、后端要重启**：前端是发静态文件给 Nginx（传完即生效），后端是 Python 源码（必须重启 `zgnb-api` 才重新加载）。
3. **数据是单向的**：本地 → 服务器会**覆盖**；网页上改的自选股只存在于服务器数据库里，下次传 db 上去就没了。

先按 `.\update_server.ps1` 跑一次练练手（什么都没改也没关系，等于原样重传一遍），看到健康检查通过，你就完整掌握这个流程了。
